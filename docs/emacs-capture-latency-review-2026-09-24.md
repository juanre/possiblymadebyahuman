# Emacs capture latency review — 24 September 2026

## Report and cause

The owner reported unacceptable keyboard latency after about 842 words. Source
inspection found two synchronous durability operations in each mutation hook:
the event journal append requested fsync, then a metadata replacement requested
fsync and rename. Work was independent of history length, but keyboard response
still depended on disk latency. Checkpoint-result callbacks also saved metadata
synchronously. Earlier scalability evidence measured aggregate throughput with
observation disabled; it did not establish interactive responsiveness on slow
storage.

The original 200-edit local microbenchmark measured a median 0.36 ms, p95
0.47 ms, and maximum 7.11 ms. This fast local filesystem did not reproduce the
owner's exact delay. Deterministic tests therefore gate storage completion and
reject filesystem writes or process launches from the editing hook.

## Implementation

- Interactive hooks timestamp and enqueue only numeric events. The queue and
  recent-event tail are each capped at 256 events. A full queue locks that
  buffer until durable acknowledgement; errors retain events and require retry.
- A persistent local Node worker commits new journal lines, fsyncs, atomically
  replaces/fsyncs bounded metadata, then acknowledges the resulting count and
  byte cursor. It does not read preceding journal history during append.
- Startup readiness and credit-controlled frames bound each Emacs pipe send to
  4096 encoded bytes. One request can be in flight. The worker bounds aggregate
  input, rejects empty/malformed/out-of-order frames, and distinguishes receipt
  of a frame from durable acknowledgement of a complete request.
- Pending ownership and acknowledged cursors advance atomically with keyboard
  quits inhibited. Metadata changes during a request remain dirty and are saved
  afterward. Checkpoints describe only the acknowledged journal prefix.
- Failure retains the exact immutable request. Retry reuses byte-identical
  complete or partial suffixes instead of duplicating or blindly truncating
  them. A deterministic private staging file allows retry after worker death
  without accumulating abandoned temporary files.
- Normal close, exit, pause, rename, and publication drain pending writes before
  changing ownership or immutable record state. Batch Lisp retains synchronous
  persistence. No format, record hash, or API migration changed.

An abrupt process or machine failure can lose events not yet durably saved.
Normal lifecycle operations drain them. This is documented rather than claiming
that returning from the editing hook implies persistence. Document text still
needs ordinary Emacs saving.

## Review and evidence

An independent agent reviewed persistence ordering, ownership, retries,
backpressure and transport. Review identified and resolved an interruptible ACK
commit, first-request pipe backpressure, and empty-frame memory growth. A second
agent implemented and tested the disk worker and native failure scenarios.

`node --test tests/emacs-producer.test.mjs tests/emacs-lifecycle.test.mjs
tests/emacs-async-recovery.test.mjs tests/emacs-journal.test.mjs
tests/emacs-writer.test.mjs tests/emacs-background-storage.test.mjs`:
**121 passed, zero skipped.** Coverage includes slow storage, exact event order,
durable checkpoint prefixes, metadata changes while saving, crash after commit
before ACK, retry, fragmented transport replies, bounded frames and queues,
major-mode/read-only bypass behavior, idle worker failure, close, rename and
discard. Nine deployment/documentation checks also passed. Lisp compilation
with free-variable, unresolved-call, argument, redefinition and obsolete checks
reported no warnings; its generated bytecode was removed.

`node scripts/benchmark-emacs-journal.mjs 4000000 400` uses the interactive
persistence pipeline, a 96 MB Node heap limit, and two-year event timestamps:

| Existing events / buffer characters | Editing p50 | Editing p95 | Maximum edit | Foreground write bytes |
| --- | ---: | ---: | ---: | ---: |
| 100 | 0.0041 ms | 0.0060 ms | 7.4871 ms | 0 |
| 4,000,000 | 0.0041 ms | 0.0060 ms | 0.0551 ms | 0 |

Each case captured 400 more events. The large case retained a 256-event tail,
712-byte metadata and a 462-byte checkpoint descriptor. Full recovery took
20.96 seconds in the synchronous benchmark; interactive recovery remains in a
background worker. Editing timings measure hooks; pipeline waits are excluded
and tested separately by the gated-storage cases. These measurements describe
this machine and fixture, not every Emacs configuration.

A one-off live reload check used the actual previous committed Lisp source:
it captured two events, loaded the updated source without closing the buffer,
and captured two further events while rejecting foreground writes. The session
identity remained unchanged; all four events were saved once in order, and
closing stopped the worker and released both ownership locks. Temporary copies
of the old source and the verification fixture were removed.
